## 0 为何需要这份规划（背景）

当前应用已可正常发布（v1.2.4）。但代码体量为支撑「接连续加功能」做了体检，结论：

- `renderer/app.js` ≈ **4498 行 / 158 个函数**，渲染、事件、主题、表格、批量、初始化全在一个文件 —— 最大的维护隐患。
- `main.js` 918 行、`note.js` 1155 行。
- **DOM 序列化逻辑重复**：`readRichContent` / `wireImages` / `wireTables` / `uid` 在 app.js 和 note.js **各一份**，改序列化协议要改两处。
- **硬编码魔法数字**：画布 2600×1800、网格 260/230、间距 18 散落多处，无法统一调整。
- `state.settings.xxx` 被直接读取 200+ 次，无「取值 / 默认值 / 版本迁移」单一入口。
- 已开始模块化：抽出 `renderer/board-layout.js`（纯布局逻辑，UMD 双模式），并接入 `arrangeNotes` / `nextGridPosition`，实现「行为不变 + 可单测」。
- **单测基线：55 → 71（阶段 A 完成）→ 75（排序/一键整理联动改造）→ 91（架构优化：sort-state / table-logic 抽纯）→ 93（列表视图排序修复）。**

**阶段 A 已完成（本节基线更新：单测 55 → 71 → 75 通过）。** 阶段 A 的 A1~A4 已全部做完，详见 `## 2 阶段规划`。

**验证过的结论**：「拆模块 + 抽纯逻辑 + 单测」这条路线**可行且安全**，不会牵动 UI 渲染层。后续按此方向推进。

## 3 已建立的工程约定（新改动必须遵守）

- **纯逻辑放独立模块**（像 `board-layout.js` / `logic.js` / `state.js` / `rich-content.js`）：UMD 双模式，Node 可测 + 页面可用。
  - `board-layout.js`（BoardLayout）：`LAYOUT` 布局常量 / `gridCols` / `overlapsAny` / `nextGridPosition` / `arrangeShelf` / `arrangeGrid` / `arrangeCompact`（紧凑填空排布，带阅读顺序单调约束，保证不重排、不重叠、不越界）/ `initPositionAll`（为缺 `positionAll` 的旧数据补「全部」位置，已有位置保持不动）。
  - `state.js`（StateLogic）：`DEFAULT_SETTINGS` / `getSetting` / `migrateData` / `migrateNote` —— settings 默认值、取值入口、数据迁移的单一来源。
  - `rich-content.js`（RichContent）：`readRichContent` / `uid(prefix)` —— DOM→marker 序列化单一来源；与 logic.js 的 `renderRichContent`（marker→HTML）互逆。
  - `sort-state.js`（SortState）：`resolveScope`（分组筛选→排序/布局两作用域）/ `posOf` / `writePos`（视图位置作用域读写，`'all'` 用 `positionAll`、其余用 `x,y`）/ `readOrderFromLayout`（画布读序）/ `reorderScoped`（只重排视图内便签）/ `ensureOrderRefs`（规整排序数组）—— 排序/布局作用域单一来源，app.js 的 `effPos`/`setEffPos`/`activeGroupId`/`layoutScopeKey`/`ensureOrder`/`saveCurrentOrder` 均为其薄封装或调用方。
  - `table-logic.js`（TableLogic）：`newTable` / `tableAddRow` / `tableAddCol` / `tableRemoveRow` / `tableRemoveCol` / `tableMerge` / `tableSplit` —— 表格数据纯逻辑单一来源，app 视图与钉窗（note.js）共用，不再各留一份。
  - `settings-panel.js`（SettingsPanel，UMD）：主题 / 字体 / 语言 / 设置面板。
  - `notes-view.js`（**经典脚本，非 UMD**）：便签渲染 / 表格 DOM 胶水 / 待办区 / 主渲染 / 回收站 / 批量 / 颜色分组弹窗。含顶层 `let` 表格状态（`activeTableEl` 等），被 app.js 的 `init` 读取，故不能包进 UMD 工厂（否则 app.js 访问不到）。若要 Node 测，需把该 `let` 状态改为可注入参数。
- **位置/排序作用域**：每个便签有两套位置——分组/未分组用 `x,y`，「全部」用 `positionAll`；排序有全局 `noteOrder` 与分组 `groupOrders[gid]`，布局快照键 `orderLayouts[layoutKey]`（`'_all'`/`'_ungrouped'`/分组 id）。**新增/改动排序或位置逻辑必须走 `sort-state.js` 纯函数并补单测**，否则会重现「全部按旧 x,y 排序」「未分组覆盖全部」「保存清空分组顺序」「切分组再切回被重排」等历史 bug。
- **改序列化协议（`[[img]]` / `[[align]]` / 高亮等 marker）必须 `readRichContent ↔ renderRichContent` 双向同步 + 单测**，否则会"改一处崩一处"（历史教训：`[[align:left]]` 泄漏成文字、`[` 累积、✕ 按钮乱飞均因此）。
- **IPC 契约**：新增/改名 `window.api.*` 必须同步 `preload.js` 与 `main.js`（`ipc-contract.js` 会在 dev 启动校验，缺 handler/sender 直接抛错）。参考 `tests/ipc-contract.test.js`。
- **双语必同步**：新增文案在 `logic.js` 的 `I18N` 里 zh+en 都补（主表与 `I18N_MERGED`），`mergeI18n` 校验键一致。
- **回归检查**：`node --check main.js preload.js renderer/app.js renderer/note.js renderer/logic.js renderer/board-layout.js renderer/state.js renderer/rich-content.js renderer/settings-panel.js renderer/notes-view.js renderer/sort-state.js renderer/table-logic.js` + `npm test` + `npm run test:e2e`。

## 8 阶段 B 前置：自定义排序 & 一键整理 联动改造（已完成，基线单测 71 → 75）

> 本轮围绕「**分组独立布局**」与「**保存当前排序 ↔ 一键整理**」做了一整轮重构 + 排坑，均已通过 `node --check` + `npm test`（**75 通过**）+ `npm run test:e2e`（18/18）验证。

### 核心模型：视图位置作用域（分组与「全部」相互独立）
- 每个便签有两套位置：**分组位置 `x,y`**（其在所属分组/未分组画布上的位置）与 **「全部」位置 `positionAll`**（「全部」视图用）。
- 新增全局工具（app.js）：`effPos(n)` 取当前视图作用域下的位置（「全部」取 `positionAll`，否则取 `n` 本身）；`setEffPos(n,x,y)` 写当前作用域位置（「全部」写 `positionAll`，否则写 `x,y`）。
- `ensureAllLayout()`：进入「全部」视图时为**没有 `positionAll`**（旧数据）或位置重叠的便签自动分配互不重叠的「全部」位置，已有且无重叠的保持不变（不覆盖手工布局）。

### 一键整理算法（`board-layout.js` 新增 `arrangeCompact`）
- 替换原来按固定 260×230 网格扫描的 `nextGridPosition`（对大/小便签会乱排、重叠）。
- `arrangeCompact(notes, maxX, opts, ...)`：把每个便签放到**最低且最左、能放下、不与已放便签重叠**的位置，填满宽/高便签旁的空隙。
- **关键**：落点带有**阅读顺序单调约束**（行优先、行内按 x），保证**视觉阅读顺序 = 传入顺序**（此前在「全部」视图大中小混合时会跳到靠上/靠左的空位打乱顺序，已修复）。
- 同样在 `nextGridPosition` 加了**画布宽度约束**（`x + w > canvasW` 则跳过换行），避免超大便签被挤到画布右缘之外。
- 排序用 `getSortedNotes`（尊重自定义排序）。

### 一键整理联动逻辑（`app.js` `arrangeNotes` / `saveCurrentOrder`）
- `saveCurrentOrder`（保存当前排序）：记录阅读顺序 + **布局快照**（`settings.orderLayouts[作用域] = { noteId: {x,y} }`），写入当前作用域（分组用 `groupId`，全部用 `'_all'`）。
- `arrangeNotes`（一键整理）：
  - **仅当 `settings.sortMode === 'custom'` 且该作用域存在快照**：恢复快照位置（setEffPos 写回）——回到当初保存时的布局。
  - **其它排序模式 / 无快照**：退回普通紧凑整理（按当前排序模式排序），不恢复、不强制改 `sortMode`。
- 整理后调用 `renderSortPanel()` 让排序面板与画布顺序一致。

### 排序面板作用域跟随视图（`settings-panel.js` `setFilter`）

### 拖拽/缩放后增量渲染缓存不同步（**重要 bug，已修复**）
- `renderAll()` 的**增量渲染**：每张便签 DOM 存 `el.__snap`（指纹），指纹未变则跳过重建。
- `startDrag` / `startResize` 直接改 DOM 的 `left/top/width/height`，但**没更新 `el.__snap`**，导致「拖动后一键整理」时：state 已恢复到快照位置，但指纹命中旧 `__snap` → 增量渲染跳过 → **DOM 停在拖动后位置（用户看到『完全不动』）**。
- 修复：`startDrag`（含批量）与 `startResize` 结束时更新 `el.__snap = noteFingerprint(n)`。

### 视觉反馈 / 排布范围
- 一键整理按**可视画布宽度**（`$('#canvas').clientWidth`）打包，确保整理后所有便签落在窗口可视范围内（而非固定 2600 宽画布导致右侧便签超出视口）。

### 已确认的坑 / 约束（勿回退）

- **不要**把 `initPositionAll` 改回「对已有 positionAll 的便签重新分配」或在 renderAll 里跑，否则「全部」视图拖动后保存会弹回、切换分组再切回会重新排开（详见上文本轮修复）。
